## 第一部分 · RSI 规格评价

### 1.1 规格本身：设计方向对，工程内容不足

| 维度 | 评价 |
|---|---|
| 问题定义 | **好。** 三层层级（上下文 / 外部制品 / 模型参数）划分清楚，明确只做第 2 层 |
| 安全性设计 | **好，且罕见。** 静态死锁护栏 + 不可变禁区是正确方向。多数自我进化方案没有这一层 |
| 验证设计 | **对，但缺件。** 双集（边界集 / 保留集）+ McNemar 是正确口径。但数据集不在库内 |
| 实现内容 | **不足。** §4.2 的伪代码不能直接实现。见下 |

### 1.2 实测：规格与实现六处不符

| # | 规格写 | 实况 | 证据 |
|---|---|---|---|
| 1 | `:online-trace Boolean` / `:offline-evolver String` | **解析器不接受这两个字段**。形状是固定三元组 | `compiler/agentlisp_compiler.rkt:205` 只匹配 `(list ':evolution mt iv vg)`；全仓 grep `online-trace`/`offline-evolver` 零命中 |
| 2 | 突变目标 4 个（含 `'prompt-patches`） | 白名单只有 **3** 个 | 同文件：`'(:pattern-macros :skills :harness-retry)` |
| 3 | 不变量 4 个（含 `'model-provider`） | 白名单只有 **3** 个 | 同文件：`'(:kv-alignment :workspace-root :forbidden-commands)` |
| 4 | §3.3 源码范例 | **不存在** | `git ls-files` 无 `repair_agent_rsi.al` |
| 5 | §3.3 范例的语法形态 | **不是现行语法**。范例写 `(:model :provider …)` 平铺；现行解析要求 `(:context :memory-policy (:markdown-fs …))` 嵌套 | 与 `examples/repair_agent.al` 对比可见 |
| 6 | §4.1「转译为 `self.evolution_config`」 | 产物里叫 **`self.EVOLUTION`**，且**全仓无人读** | grep `EVOLUTION` 于 runtime/host/scripts/tools 零命中 |

### 1.3 实测：§5 的五个测试文件，五个全缺

| 规格引用 | 实况 |
|---|---|
| `compiler/tests/test_evolution.rkt` | 缺失 |
| `compiler/tests/test_checker_evolution.rkt` | 缺失 |
| `runtime/tests/test_online_trace.py` | 缺失 |
| `scripts/bench/tests/test_evolver_gate.py` | 缺失 |
| `scripts/evolver/tests/test_git_worktree.py` | 缺失 |

**含义**：§5 的可追溯矩阵是**声明**，不是账。ISO 29148 要求每条需求有可执行验证。
按现状态，FR-EVO-1~5 五条**全部未验证**。

### 1.4 实测：RSI 的前提条件有三件不满足

| 前提 | 现状 | 影响 |
|---|---|---|
| 真实 τ²-bench 数据集 | 只有 `--dry-run` 合成数据 | McNemar 需真实分布。合成数据上的 p 值无意义 |
| `scripts/bench/tests/` | 目录不存在 | FR-EVO-4 无落点 |
| `ExecutionTraceV2` 含首错位置 | 只有 `status` + `error: str`。无首错字段、无结构化错误 | §2.2 步骤 1「定位首错」无输入 |

### 1.5 我的判断

**RSI 现在不能做。** 三条理由：

1. **它的输入不存在。** 离线进化器要吃「首错位置」。`ExecutionTraceV2` 不产这个字段。
2. **它的判据不可判。** 真实 benchmark 数据集不在库内。合成数据上算不出有意义的 p 值。
3. **它的载体不可读。** `:evolution` 已 emit 进产物，但运行时零引用。等于 RSI 的「契约」是空转。

**但方向对，值得做。** 它是唯一让 agentLisp 具备「自我改进」性质的路线。
且它的静态护栏设计（不可变禁区）比多数自我进化方案严谨。

**结论**：RSI 排最后。前置三件必须先补：证据链字段、真实数据集、契约消费点。

### 1.6 一处必须警惕的设计风险

§2.2 第 5 步写「验证通过后提交 Pull Request；**合并代码至 `.al` 源码主干**」。

自动合并自改代码到主干是高风险动作。建议改为：

- 自动**提交 PR**，但**必须人工批准才合并**；
- 理由：McNemar p<0.05 只证明统计显著，不证明改动符合意图。两者不同。

**这条我建议写进计划作为硬约束。**（未与规格作者确认。）

## 第二部分 · 统一诊断

### 2.1 全部发现归为一个病

三线看似无关，实测后是**同一个病**：**声明与消费脱节。**

| 线 | 症状 | 数量 | 证据 |
|---|---|---|---|
| 投产 | 模式 kind 只声明不消费 | **8 / 21** | handler 只 `validate`+`summary` |
| 投产 | 注册表条目无 handler | **2** | `memory`、`multi-agent` |
| AMS 搬迁 | AMS 的 mode/primitive 层与 agentLisp 的 kind 层语义重叠 | 2 套 | 见 F-AMS-4 |
| RSI | `:evolution` 已 emit，运行时零引用 | **1** | grep `EVOLUTION` 零命中 |
| RSI | §5 五个测试文件全缺 | **5** | 逐个核对 |

**合计：18 处声明与消费脱节的实例。**

另有独立证据：AMS 自己的审计文档承认 PAT03/06/07/09 的语义
「只以字符串形式存在于 `:system-prompt`，Core AST 里没有可执行结构承载」。
**两个系统独立踩了同一个坑。**

### 2.2 为什么必须一个计划

三线共用同一套基础设施：

| 基础设施 | 投产线要用 | AMS 搬迁要用 | RSI 要用 |
|---|---|---|---|
| 行为槽位模型（F-AMS-6） | ✓ 修 8 个仅声明 | ✓ | ✓ 加 `evolve` 槽位 |
| 图模型（F-AMS-1） | — | ✓ | ✓ 离线循环的载体 |
| 状态声明（F-AMS-3） | — | ✓ | ✓ 证据传递 |
| 契约内容校验（B5） | ✓ | ✓ | ✓ |
| 门禁（B7） | ✓ | ✓ | ✓ |

**分头推进 = 同一判断多处实现。** 违反判据 C4。

### 2.3 统一的不变式

> **每条声明的语义，必须有一个运行时可观测的消费点。无消费点者，编译期拒绝或显式登记为声明层。**

这条不变式同时治 18 处实例。它是本计划的核心。

## 第三部分 · 阶段计划

8 个阶段。顺序由依赖决定，不由优先级决定。

### P0 · 止血（1 阶段，最紧）

| 项 | 内容 | 判据 |
|---|---|---|
| P0-1 | 修 E2E 红灯 | 根因是探针脚本路径，不是产物缺陷。子进程传 `PYTHONPATH` 并登记「产物依赖 runtime 包」 |
| P0-2 | 提交门禁（测试 + ruff + 判据） | 注入红灯被拒 |
| P0-3 | 口径三处对齐（README / LANDED 注释 / patterns README） | 数字一致且有脚本核对 |

**为什么最紧**：红灯在 main 上。任何「已验证」的说法都不成立。
门禁不含测试 ⇒ 已发生两次带红提交。

### P1 · 模型层（核心重构，三线共用）

| 项 | 内容 | 判据 |
|---|---|---|
| P1-1 | **行为槽位模型**（F-AMS-6 / D3） | 每个 kind 声明占用的槽位；`LANDED` 只收槽位非空者；槽位数 == 运行时调用点数 |
| P1-2 | 防膨胀规则入判据 | 新增槽位必须同时新增调用点 + 断言 |
| P1-3 | 依赖与组合校验移编译期（F-AMS-4） | 互斥/要求/蕴含三类关系编译期判定；缺依赖失败，不静默失活 |
| P1-3a | 模式异常不拖垮 agent（原清单 #11） | handler 抛错被捕获 + 留痕 + 测试 |
| P1-4 | 契约内容校验（B5） | 21 份契约的栏位（id/输入/期望/反证/端口/不承诺）**已实测 21/21 齐备**；缺的是**判据不校验栏位内容**。本项把人工约定变成机器拦 |

**为什么在 P1**：它是模型。后改则 21 个 kind 重写两遍。
且它同时是「8 个仅声明」的根因修复，也是 RSI 加 `evolve` 槽位的前提。

## 第六部分 · 决策记录与待办

### 6.1 已决定：发 PyPI（2026-10-14，用户决定）

**决定**：agentLisp 发布到 PyPI。

**背景**：仓库原为「不发 PyPI」决策。机制已存在但默认关闭：
`.github/workflows/release.yml:266` 的 `publish-pypi` job 触发条件为
`vars.PUBLISH_PYPI == 'true'`，默认未设置。

**硬顺序（不可调换）**：

```
P5-1 修 P0（v2.3.1） → P5-3 真实环境验收 → P5-2 拧开关发 PyPI
```

**为什么顺序不可换**：PyPI 版本**不可撤回**，只能 yank。已下载的用户保留该版。
当前 v2.3.0 含 P0（带模式的产物无法 import）。先发即永久公开该缺陷。

**分两步走（建议）**：

| 步 | 目标 | 判据 |
|---|---|---|
| 1 | TestPyPI 试点 | `workflow_dispatch` 选 `testpypi`，装包能 `agentlisp --version` |
| 2 | 正式 PyPI | 设 `PUBLISH_PYPI=true`，装包能编译一个 `.al` |

**风险与守**：

| 风险 | 守 |
|---|---|
| 发了含缺陷版本 | 顺序硬约束 + TestPyPI 试点 |
| 包名被占 | 先核对 PyPI 上 `agentlisp` 的现状（我未联网查） |
| 后续版本无法回退 | 只在 P5-3 通过后发；版本号只增 |
