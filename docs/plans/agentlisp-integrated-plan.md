> 方法：先建唯一事实基线，再按两个正交轴切分，最后给顺序与门。
> 日期：2026-10-14 · 基线提交 `f06f19d`（工作区干净，本地 = 远端 main）

## 零、两个必须先纠正的概念错误

这两条是整合的地基。不先纠正，后面所有计数都会重复计。

### 错误 1：把「接线」当成行为进入运行时的唯一通路

行为进入运行时**有两条路**：

| 通路 | 机制 | 例子 |
|---|---|---|
| 接线 | handler 覆写运行时入口（`on_init`/`before_turn`/`on_tool_call`/`after_turn`），或提供运行时查询的方法（`order`/`policy`/`verify_evidence`/`validate_payload`/`evaluate`/`budget`） | `priority` 的 `order`、`hitl` 的 `on_tool_call` |
| 产物配置 | 编译期 emit 出的 `harness_config` 等键，由 `BaseHarnessV2` 直接消费 | `:constrain :forbidden-commands` 由 `base_harness_v2` 的 `_contains_forbidden_token` 强制 |

**后果**：只说「N 个 kind 被真消费」会把通路 2 的行为漏算，也会把通路 1 的缺失误判为「行为完全没生效」。

### 错误 2：把「注册表成员」「产物声明」「运行期语义」三层混为一谈

| 层 | 含义 | 可机械判定 |
|---|---|---|
| L1 注册表 | 该 kind 在 `pattern_registry.rkt` 有条目 | 是 |
| L2 产物声明 | `.al` 声明后，产物 `self.PATTERNS` 出现该 kind + 键 | 是 |
| L3 运行期语义 | 该 kind 声称的行为在运行时真的发生 | 需逐条验证 |

「21/21 运行时落地」是口号。它同时指 L1/L2/L3，三层事实不同。

## 二、MECE 主轴：能力交付链（8 阶段）

按「谁在哪个阶段做什么」切分。互斥（每阶段一个行为主体、一个动作类型），穷尽（能力从表达到投产必经这 8 段）。

| 段 | 阶段 | 行为主体 | 输出 |
|---|---|---|---|
| S1 | 设计输入 | 人 / 外部工具 | 需求、材料 |
| S2 | 语言表达 | `.al` | 源文件 |
| S3 | 静态判定 | 编译器 checker | 错误码 / 通过 |
| S4 | 产物生成 | 编译器 emitter | Python 产物 |
| S5 | 初始化握手 | 运行期 `PatternRuntime` | 已载入 handler |
| S6 | 运行期消费 | `BaseHarnessV2` | 行为 |
| S7 | 运行期验证 | 测试 / 判据 | 通过 / 失败 |
| S8 | 投产 | 发布流程 | 可用制品 |

**为什么这样切**：S5 与 S6 必须分开。S5 只回答「handler 载入了吗」，S6 回答「行为发生了吗」。
现在 12 个 B 类 kind 的问题正好卡在 S5→S6 之间：载入了，但不做事。

## 三、MECE 第二轴：能力四个正交维度

每一对都独立：有≠被调用，被调用≠正确，正确≠已验证。

| 维度 | 问题 | 判据 |
|---|---|---|
| D1 存在 | 代码里有没有 | 注册表 + HANDLERS 成员 |
| D2 消费 | 运行时调不调 | handler 的运行时入口 或 产物配置被 harness 读 |
| D3 正确 | 被调用时行为对不对 | 契约 + 反证测试 |
| D4 验证 | 有没有机器拦的证据 | 契约内容校验 + E2E 断言 |

```
B7 门禁 ─────────────┐
                     ├─> B5 契约内容校验 ──> B3 接线 ──> B6 E2E
```

| 步 | 依据 |
