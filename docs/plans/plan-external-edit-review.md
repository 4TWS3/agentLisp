判据：B12 完成后，那 4 个 kind 走 handler 协议方法，接线数**仍为 13**，不得下降。

### 3.2 E2E 红灯的根因不是产物缺陷

计划写「产物在子进程里跑不起来」。

实际报错：

```
File "/tmp/.../e2e_out.py", line 16, in <module>
    from runtime.base_harness_v2 import BaseHarnessV2, build_kv_aligned_context
ModuleNotFoundError: No module named 'runtime'
```

复算：

| 检查 | 结果 |
|---|---|
| 仓库根下 `import runtime` | 成功 |
| 探针脚本位于 `/tmp` 且 `cwd=仓库根` | `sys.path[0]` = `/private/tmp` → 失败 |

**根因**：测试的探针脚本写在 `tmp_path`，Python 把脚本所在目录放进 `sys.path[0]`，**不放 cwd**。

**性质**：测试环境问题，不是产物缺陷。产物按设计依赖已安装的 `runtime` 包。

**证据**：全仓唯一的 E2E 红灯只在 `tests/` 选择集下出现。未加 `sys.path` 插入的日志。

**修法二选一**：

| 路 | 做法 | 代价 |
|---|---|---|
| A | 子进程传 `PYTHONPATH=仓库根` | 一行；测试通过；不回答架构问题 |
| B | 让产物自包含（内联 harness） | 大改；与「产物继承 BaseHarnessV2」的设计冲突 |

**A 是对的，但要登记**：产物运行要求 `runtime` 包可导入。这是运行前提，应写进 README 与 SRS。
**B 是设计变更**，须你决策。

## 四、我方同一轮的新发现（比上面更关键）

### 4.1 消费面其实是三个，不是一个

| 面 | 机制 | kind 数 |
|---|---|---|
| ① handler 协议 | 覆写 `on_init`/`before_turn`/`on_tool_call`/`after_turn`，或提供 `order`/`policy`/`verify_evidence`/`validate_payload`/`evaluate`/`budget` | 9 |
| ② `PatternRuntime` 分派 | `verify_observation` 里的 kind 字符串分支 | 4 |
| ③ `api(kind)` | 纯取 handler 的**测试用访问器** | 不构成运行期消费 |

**③ 不算消费。** 它的 docstring 自己写明「供契约测试打纯函数」。

### 4.2 「8 个仅声明」的测试其实通过了，但走的是 ③

以 `chain` 为例（`tests/patterns_runtime/test_chain.py`）：

| 断言 | 走哪条路 | 是否证明行为生效 |
|---|---|---|
| `h.patterns.api("chain")` 取到 handler | ③ 测试访问器 | ❌ 只证明 handler 存在 |
| `"pattern:chain" in build_context()` | 指令注入 | ❌ 只证明指令进了上下文 |
| `next_step` 的返回值 | 契约测试直接调纯函数 | ❌ 引擎从不调用它 |

**结论**：这 8 个 kind 的测试全绿，但**没有一条断言证明引擎会消费该行为**。

这正面解释了「单测全绿却漏掉 P0」的同一形态：**测试走的路与生产走的路不是同一条**。

### 4.3 契约栏位其实 21/21 齐备

计划 §12.2 与外部清单说「空契约或漏栏」。**实测不成立。**

| 栏 | 出现份数 |
|---|---|
| id / 输入 / 期望 / 反证 / 端口 / 不承诺 | **各 21/21** |

所以 B5 的真实缺口**不是栏位缺失**，而是：**A11 判据只校验契约文件存在 + 测试引用 id，不校验栏位内容。**
契约靠人工守，不靠机器拦。

**B5 的正确表述**：把已存在的栏位约定变成机器拦。不是去补栏位。
